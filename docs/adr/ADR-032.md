# ADR-032: GPU2D / DMA2D

## 状态

Accepted（DMA2D 探针真机 MEASURED；**PARTIAL** —— DEV boot 下 DMA2D 对
SRAM 的写入被 RISAF 防火墙对所有 CID 拦截，与 ADR-029 ADC-DMA 同因，
非驱动缺陷、无法从固件层修复，见「实现现状（真机 MEASURED）」）

## Phase

P4

## 目标

> GitHub Issue: #37
> 验证级别: MEASURED

实现 STM32N6 GPU2D / DMA2D（Chrom-ART）驱动，
用于 2D 图形硬件加速（填充、复制、混合、格式转换）。

## 实现现状（真机 MEASURED，2026-07-30）

**结论：DMA2D 在当前 DEV boot 配置下无法写入 SRAM——被 RISAF 防火墙
对所有可编程 compartment ID（CID 0..7）一律拦截。故本 ADR 判定 PARTIAL。**

为在无示波器、无外部接线的真机上判定 DMA2D 可用性，新增了一个去风险
探针 `stm32n6_dma2d_probe()`（`dma2d_test` builtin）：使能 RIFSC + DMA2D
时钟，通过 RIFSC `RIMC_ATTRx[8]` 逐个把 CID 0..7（secure+priv）赋给 DMA2D
（master index 8），每次跑一个 register-to-memory 填充，把已知字
`0xDEADBEEF` 写入一块 cache-line 对齐的 SRAM 缓冲，再读回校验。用 sentinel
预填 + D-cache clean/invalidate 严格区分「真写入」与「被 RAZ/WI 静默丢弃」。

真机实测（两次运行，其余回归 15/15 绿）：

- 每个 CID 0..7 的 R2M 填充都被丢弃：`ISR=0x2`（TCIF 置位、无错误）但
  缓冲读回仍是 sentinel `0x11111111`，与 GPDMA1 的防火墙特征完全一致。
- 包括 CID 1（Cortex-M55 CPU 呈现的 CID、ST 官方示例授权的那个）也被拒。

**判读：** DMA2D 本身工作正常（能配置、能跑、TCF 置位），RIMC 可写、CID
可重编程——但 DEV boot 下管辖 CPU AXISRAM 的 RISAF 只放行 CPU 核自身的
访问路径，不接纳任何可编程总线主设备的 CID 写入。这与 ADR-029 的
GPDMA-to-SRAM 阻塞是**同一类** boot-mode RISAF 授权限制：需要 Secure-world
/ FSBL 组件在启动时编程 RISAF region 授权（当前单世界 secure-only DEV boot
没有该组件），或改用 flash-boot / XIP 的授权方案。不是 NuttX 驱动可修复的
缺陷。

> **后续决定性验证（2026-07-31，`dma2d_unlock`）**：为排除「只是没在区域侧
> 授权」的可能，另写 `dma2d_unlock` 探针在 RISAF2 建 region 覆盖 DMA2D 缓冲、
> 使能、白名单授权 CID0|CID1，并逐一设 DMA2D 的 RIMC CID——**全程寄存器回读
> 确认 region（CFGR=0x101 BREN=1、边界、白名单）与 RIMC override 均生效**，
> 但 DMA2D 写 SRAM 对 CID 0..7 仍全部被丢（含 CID1）。判据：CPU@CID1 通过、
> DMA2D@CID1 被拦、二者 CID 相同 → 拦截依据是**主设备总线身份**，非 region
> 白名单。这把「NuttX 无法解锁」从推断升级为**寄存器回读 MEASURED 定论**：
> 任何 region+RIMC 配置都不行；FSBL/secure-world 能否解属未测、不作断言。
> 详见 ADR-039「决定性更正」节与 [[hw-stm32n6-risaf-dma2d-grantable-gpdma-not]]。

因此 ADR-032 决策中「DMA2D 作为 display_hal 内部填充加速引擎」在 DEV boot
下不可落地；`display_fill_rect()` 若需硬件加速，须待 flash-boot 授权方案
或退回 CPU memset 软件填充。SRAM 目标的 DMA2D 加速留待 boot 模式演进后
再验证。

## 上下文

STM32N647X0 有 DMA2D（Chrom-ART）加速器，特性：
- 矩形填充（Solid Fill）
- 矩形复制（Copy）
- 像素格式转换（RGB565↔RGB888↔ARGB8888）
- Alpha 混合（全局/逐像素）
- 硬件 CLUT（颜色查找表）

DS14791 Section 11: DMA2D。
DMA2D 卸载 CPU 的 2D 图形操作，提升 GUI 性能。

## 决策

将 GPU2D/DMA2D 作为显示子系统的内部加速引擎，集成到 display_hal 中，而非独立驱动：

1. **定位**: DMA2D 作为 LTDC 前景层的绘制加速器，不单独暴露设备接口
   - 矩形填充（Register-to-Memory 模式）: 用于清屏、绘制纯色色块
   - 矩形复制（Memory-to-Memory 模式）: 用于 UI 元素快速搬运
   - Alpha 混合暂不使用（前景层本身支持全局 Alpha）

2. **使用场景**:
   - 检测框（bounding box）绘制: DMA2D 填充窄矩形条
   - 统计面板背景: DMA2D 填充半透明色块
   - 前景层清除: DMA2D 全屏填充透明色（0x0000）

3. **集成方式**: 封装在 `display_hal.c` 内部
   - `display_fill_rect()` 接口底层调用 DMA2D
   - 同步等待传输完成（DMA2D TC 标志位轮询）
   - 不使用 DMA2D 中断，避免与 LTDC VSYNC 中断冲突

4. **不采用 LVGL**: 当前应用场景为简单 OSD 叠加（检测框 + 文字 + 统计信息），
   引入 LVGL 图形栈过于重量级，直接使用 DMA2D 硬件即可满足需求

实现文件：
- `app/edgesight/display_hal.h` — 包含 `display_fill_rect()` 等绘制接口
- `app/edgesight/display_hal.c` — DMA2D 初始化与矩形填充实现

## 设计

### 模块架构

```
DMA2D (Chrom-ART)
├── 工作模式
│   ├── 寄存器到存储器 (填充)
│   ├── 存储器到存储器 (复制)
│   ├── 存储器到存储器+PFC (格式转换)
│   └── 存储器到存储器+混合 (Alpha 混合)
│
├── 像素格式
│   ├── ARGB8888 (32-bit)
│   ├── RGB888 (24-bit)
│   ├── RGB565 (16-bit)
│   ├── AL88 (16-bit, Alpha+亮度)
│   └── L8 (8-bit, CLUT)
│
└── 前景/背景层
    ├── FG 输入 (前景)
    ├── BG 输入 (背景)
    └── 输出 (混合结果)
```

### NuttX 框架对接

```
DMA2D 作为 LTDC 辅助引擎:
  GPU2D 填充 → 帧缓冲
  GPU2D 混合 → 双层叠加
  GPU2D PFC → 格式适配

LVGL 集成:
  lv_draw_sw → lv_gpu_stm32_dma2d()
    → DMA2D 加速矩形填充/复制/混合
    → CPU 空闲处理复杂路径
```

### 数据流

```
矩形填充:
  CPU → 配置 DMA2D OCOLR/OMAR/OMAR+NLR
    → DMA2D 写入帧缓冲
    → LTDC 显示

Alpha 混合:
  FG 帧缓冲 + BG 帧缓冲
    → DMA2D 混合
    → 输出帧缓冲
    → LTDC 显示

## 理由

1. **轻量集成优于独立驱动**: 当前只有 display_hal 使用 DMA2D，无需 NuttX 设备驱动层的开销。
2. **不引入 LVGL**: 应用场景仅为 OSD 叠加（检测框 + 简单文字），LVGL 带来的 flash/RAM 开销和复杂度不值得。
3. **同步模式简化设计**: DMA2D 矩形填充极快（微秒级），轮询等待比中断更简单，且不会阻塞关键路径（绘制发生在非显示缓冲区上）。
4. **为后续扩展留余地**: 如需更复杂的 GUI，可在此基础上逐步引入 LVGL 的 DMA2D 加速回调。
