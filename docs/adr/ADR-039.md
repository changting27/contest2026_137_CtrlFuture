## 上下文

### 当前限制

P0 起全程 **DEV boot（BOOT1=0,BOOT0=1）**：固件由 GDB 加载到 SRAM
`0x34000400`，掉电即丢，无法独立上电启动——不满足最终产品形态。

同时，DEV boot 下 ROM 的默认 **RISAF** 策略只授权 CPU 的 CID 访问 SRAM，
未授权总线主 DMA 引擎，导致三个 ADR 卡在 PARTIAL：

- **ADR-029 ADC**：GPDMA1 写 SRAM 被防火墙丢弃（轮询模式 MEASURED，DMA 延后）
- **ADR-032 DMA2D**：DMA2D 写 SRAM 被丢弃（探针 MEASURED，填充/搬运延后）
- **ADR-036 NPU**：Neural-ART 读写 SRAM 大概率同样被丢（未验证）

### RISAF 是什么

**RISAF = RIF Security Attribute Firewall**，STM32N6 **RIF（Resource
Isolation Framework，资源隔离框架，RM0486 §7.4）** 的内存防火墙组件。RIF 含：

| 组件 | 全称 | 管辖对象 |
|------|------|----------|
| RIFSC | RIF Security Controller | 外设属性（RISUP 从设备侧、RIMC 主设备 CID 分配） |
| **RISAF** | RIF Security Attribute Firewall | **内存/地址空间**访问控制（AXI SRAM、XSPI 等） |
| RISAL | 轻量版 RISAF | 部分内部小内存 |

RISAF 对**每一笔总线事务**按地址匹配 region，再按发起者的 **CID
（Compartment IDentifier，隔离域标识）**、安全/特权属性、读写方向校验；
CID 不在该 region 授权列表 → 拦截（总线错误或静默丢写）。CPU、GPDMA1、
DMA2D、NPU 各有独立 CID。

正常产品由启动早期的 **secure software 编程 RISAF**
（`HAL_RIF_RISAF_ConfigBaseRegion` 等）把这些总线主 CID 授权进来。ST 预编译
FSBL 把 `HAL_RIF_MODULE_ENABLED` 注释掉了 → 没做这步。**注意：这里的
「secure software」在 DEV boot 下就是 M55（=TDCID）跑的 NuttX 自己**——ST
文档明确 RISAF 属 TDCID 权限、且探针实测 CIDCFGR 对 NuttX 可写，所以补上
这步**不必等 FSBL**，NuttX 早期 `__start` 即可做（详见下方「RISAF 可写性
真机探针」两小节）。FSBL 只在 flash-boot 冷启动链路才需要，与 RISAF 解锁
是两件独立的事。

DS14791 Section 6: Boot modes；UM3234: boot ROM；RM0486 §7.4: RIF/RISAF。

## 决策

本 ADR 聚焦**目标 B（掉电持久冷启动）**。RISAF 解锁 DMA→SRAM（目标 A）与
本 ADR 无关，且已被 `dma2d_unlock` 真机证伪为 **DEV boot 下 NuttX 无解**
（region+RIMC 均生效仍被拦，见状态头 ⚠ banner 与「决定性更正」节）——它既
不是本 ADR 的交付项、也不是任何 NuttX 早期启动方案能交付的。据此分阶段推进：

1. **阶段 1 — 最小 flash-boot 打通**：
   物理跳线切 `(BOOT1=0,BOOT0=0)`；复用/裁剪 ST FSBL 初始化 XSPI1 + 内存
   映射；NuttX 固件写入 flash；ROM→FSBL→NuttX 冷启动到 NSH；掉电重启不丢。
   **FSBL 只负责启动链（XSPI/内存映射/跳转），RISAF 交给 NuttX 早期启动。**

2. **阶段 2（可选）— flash-boot 默认 RISAF 策略确认**：
   UM3234 Table 4 只记录 DEV boot 的 "Clear RISAF2"，flash-boot 分支未文档化。
   冷启动后读一遍 RISAF 现状，确认 NuttX 早期编程 RISAF 的前提（region 未被
   ROM/FSBL GLOCK 冻结）在 flash-boot 下同样成立。若被冻结，才需在自定义
   FSBL 里预留 RISAF 编程窗口——**这是唯一可能把 RISAF 拉回 FSBL 的情形，
   需实测确认，默认不假设。**

3. **阶段 3（可选）— OTA/双分区**：固件持久后再叠加，本 ADR 不含。

### 安全性与砖机风险（低，可逆）

- 芯片出厂 **CLOSED_UNLOCKED**（UM3234 Table 3）：flash 启动**不需签名、
  不需烧 OTP/BSEC 熔丝**，全程可逆。
- flash 写坏可由 `(BOOT1=1,BOOT0=0)` 串口/USB DFU 启动（`.stldr` 外部加载器）
  无条件恢复重刷——**不会变砖**，是迭代出错的安全网。

## 设计

### 启动链变更

```
DEV boot (当前):
  ROM → (BOOT0=1) → SRAM @ 0x34000400 (GDB load) → _stext → nx_start()

Flash boot (本 ADR):
  ROM → (BOOT0=0,BOOT1=0) → FSBL @ flash
    → XSPI1 init + memory-mapped
    → jump NuttX (@ SRAM 或 XIP) → _stext
    → nx_start()
    (注: DMA→SRAM 的 RISAF 解锁不在此链——DEV boot 下 NuttX region+RIMC
     配置已 MEASURED 证明无法解锁, 门在主设备总线身份; flash-boot 能否解未测)

砖机恢复:
  (BOOT1=1,BOOT0=0) → 串口/USB DFU → STM32_Programmer_CLI + .stldr 重刷
```

## RISAF 可写性真机探针（MEASURED，2026-07-31）

> 验证平台: 真实 STM32N647 开发板（远程 SSH+GDB+串口，ALIENTEK N647）
> 自测程序: `risaf_probe`（`app/risaf_probe_app/`），NSH builtin
> arch 助手: `arch/arm/stm32n6/src/stm32n6_risaf_probe.c`

### 探针要回答的问题

早先 DMA2D 探针（ADR-032）扫过 CID 0..7 全被防火墙拦截，据此推断
「无法从 NuttX 固件修复」。但那只改了**主设备侧**（RIMC 里 DMA2D 的 CID），
从没碰过**内存区域侧**（RISAF region 的 CIDCFGR 白名单）。本探针单独测区域
侧：**DEV boot 下 NuttX 能不能写 RISAF 配置寄存器**——这是"改驱动无解 →
必须 FSBL"这个论断里唯一没实测过的一环。

### 方法（零强制变更，无锁死风险）

目标 RISAF21 REG[0]（实测禁用态 BREN=0、容器未锁 GLOCK=0）。**全程保持
BREN=0**：禁用的 region 不被防火墙评估，写它的 CIDCFGR 不改变 CPU 或任何
DMA 主的可访问范围。往 CIDCFGR 写 `0x00FF00FF`（CID 0-7 读使能 bit0-7 +
写使能 bit16-23）→ 读回 → 立即恢复原值。决不置 GLOCK、决不使能 region、
决不动 RISAF7（固件自身运行的 FLEXMEM）。

### 结果：三态里的 PARTIAL（不是简单的"锁死"）

```
risaf: RISAF21 CR=0x00000000 (GLOCK=0) REG0.CFGR=0x00000000 (BREN=0)
risaf: CIDCFGR before=0x00000000 wrote=0x00ff00ff readback=0x00030003
```

读回 **`0x00030003`** —— 不是全 0（纯 RAZ/WI），也不是 `0x00FF00FF`（全可写）：

| 位 | 含义 | 写 1 → 读回 |
|----|------|------|
| bit0/bit16 | CID **0** 读/写使能 | ✅ 粘住 |
| bit1/bit17 | CID **1** 读/写使能 | ✅ 粘住 |
| bit2-7 / bit18-23 | CID **2-7** 读/写使能 | ❌ 忽略 |

**修正早先判断**：CIDCFGR 寄存器对 NuttX **是可写的**（CID0/1 位真的粘住），
并非"锁死到更高特权"。只是这个 RISAF 实例硬件上只实现 2 个 compartment
（CID2-7 位不存在）。

### ST 文档背书：解锁 RISAF 属于 NuttX 权限，不必 FSBL（更正）

> 早先版本据两个探针推断「RISAF 必须在 FSBL 里配」。**此结论错误**，ST
> 官方 RIF 文档直接推翻它。保留此更正记录以说明推理链的演进。

三句 ST 官方定义（见「参考」链接）合起来决定了正确结论：

1. "**The CPU's CID is hardwired to 1.** The CID of other bus master
   peripherals is 0 by default but **can be configured by secure software**."
2. "TDCID = Trusted Domain CID … the master owning the highest access rights
   … **capable of configuring critical secure and system resources** … **The
   value is fixed after ROM code execution.**"
3. "Address spaces protected by the RISAF are by default **secure,
   privileged, and CID only.**"

DEV boot 里唯一的处理器就是 M55，它是 trusted boot 的 boot processor →
**M55 = TDCID，CID 硬连线 = 1**。TDCID 有权配置 system resource（RISAF 即
是）。第 2 句 "fixed after ROM" 冻结的是**「谁是可信域」这个身份**（ROM 之后
不能把 TDCID 改指给别的主），**不是「RISAF 配置被锁死」**。M55 始终是 TDCID，
始终能配 RISAF。这正好解释探针里 CID1 的位为何粘住——M55=CID1=TDCID，被
RISAF 承认。

**所以：解锁 DMA→SRAM 不需要 FSBL。** ST 明确它属于 "secure software"
（在 DEV boot 里就是我们的 NuttX，即 TDCID）该做的事。FSBL 唯一真正非它
不可的，只有**掉电持久独立启动**——因为 ROM 只在 flash-boot 链路才跑 FSBL，
与 RISAF 无关。

### 为什么要在启动早期配置，而两个 app 探针却没能解锁

关键澄清：**两个 app 探针从来没有真正「尝试解锁 DMA」**，所以不是「app 里
试了、失败了」，而是「app 里根本没做那件能成的事」。RISAF 放行一笔 DMA 写
需要**两把锁同时开**：

| 锁 | 寄存器 | dma2d 探针 | risaf 探针 |
|----|--------|-----------|-----------|
| ① 主设备侧：DMA 主的 CID | RIFSC_RIMC_ATTR[x] | ✅ 改了（扫 CID 0..7） | ✗ 没碰 |
| ② 区域侧：**目标 SRAM 所在活跃 region 的白名单 + 使能** | RISAF REGn.CIDCFGR + CFGR.BREN | ✗ **从没配过** | ✗ 只写了**禁用的** scratch region 并立即还原 |

- **dma2d 探针**只开了①（主设备 CID），从没开②（区域白名单）。只开一把锁，
  DMA 当然进不去——这符合预期，不代表「配不了」。
- **risaf 探针**只往**禁用**的 scratch region（REG[0]，BREN=0）写值验证寄存器
  可写，**故意不碰**管辖数据的活跃 region、也没使能任何 region。它证明的是
  「CIDCFGR 能写」，不是「尝试解锁」。

**能成的那一步（谁都没做）**：把 DMA 目标缓冲放进一块**专属 SRAM region**，
使能它（BREN=1）并把 DMA 主的 CID 加进它的读写白名单。ST 文档说 TDCID(M55)
随时有权做——**技术上 app 里也能做**。那为何仍应放在早期 `__start`？两个
务实原因（非特权原因）：

1. **内存布局在 `nx_start()` 前还是「处女地」**。app 阶段堆已初始化、栈/缓冲
   已按 linker 落位，此时去重新划分/使能一块覆盖某段 SRAM 的 region，可能把
   正在使用的内存从运行中的系统脚下抽走。早期启动尚未 heap init，可以干净地
   先定义「哪块 region 覆盖 DMA 缓冲、授权给谁」，再放任何东西进去。
2. **绝不能动 CPU 自己代码/栈所在的 region**。ROM 给固件运行的 SRAM 用的是
   **RISAF2**（起始 0x400 偏移，ROM 要求 FSBL/固件在此，CID1-only）。dma2d
   探针的缓冲恰是固件 BSS 里的静态数组，落在这块 CPU-SRAM region——想授权它
   就得改「CPU 正在其上运行」的 region，运行时这么做有**把 CPU 自己锁出内存**
   的风险。正解是让 DMA 缓冲落在**另一块**独立 region（如 AXISRAM，归
   RISAF21/22），只授权那一块——而把 DMA 缓冲与 CPU-SRAM 干净分离、并在使用
   前建好授权，最自然的时机就是早期 `__start`。

**净结论（更正后）**：解锁 DMA→SRAM **在 DEV boot 的 NuttX 早期启动即可完成**，
不需要 FSBL；关键是（a）给 DMA 缓冲划一块专属 region，（b）在 `nx_start()`
前使能它并把 DMA 主 CID 加进白名单。之前的探针都没做②，所以看起来「还是被
拦」。**FSBL 仅为掉电持久启动（ADR-039 的 B 目标）所需，与 RISAF 解锁无关。**

## 决定性更正：region + RIMC 解锁真机实测失败（MEASURED，2026-07-31）

> 自测程序: `dma2d_unlock`（`app/dma2d_unlock_app/`），NSH builtin
> arch 助手: `stm32n6_dma2d_unlock_probe()`（`stm32n6_dma2d.c`，
> `CONFIG_STM32_DMA2D_UNLOCK`）

上面「ST 文档背书」「为什么要在启动早期配置」两节主张的解锁配方——**给 DMA
缓冲划专属 region、使能它（BREN=1）、把 DMA 主 CID 加进白名单**——被真机
按方配置后**证伪**。保留那两节以记录推理链演进；结论以本节为准。

### 方法（照配方精确执行 + 全程寄存器回读）

`dma2d_unlock` 在 RISAF2 REG0（RISAF2 管辖固件与缓冲物理所在的 0x34000000
AXISRAM）建一块覆盖 DMA2D 缓冲的 region：STARTR/ENDR 为相对 0x34000000 的
字节偏移（4KB 粒度、上下界 inclusive），白名单 = CID0|CID1 读写，CFGR =
BREN|SEC。随后用 RIMC 逐一把 DMA2D 主设备呈现为 CID 0..7 各跑一次
register-to-memory 填充。**关键：编程后回读 region 四个寄存器、每次 sweep
后回读 RIMC_ATTR[8]**，以区分「配置没生效」与「配置生效但仍被拦」。

### 结果：两把锁都确认打开，写仍被丢

```
RISAF2 REG0 readback CFGR=0x00000101 (BREN=1) ST=0x00062000 EN=0x00062fff CID=0x00030003
CID 0 wrote_attr=0x300 RIMC_rb=0x300 -> dropped (firewalled)
CID 1 wrote_attr=0x310 RIMC_rb=0x310 -> dropped (firewalled)   ← CID1 在白名单、CPU 用它写同块 SRAM 正常
CID 2..6 wrote_attr==RIMC_rb        -> dropped
CID 7 wrote=0x370 rb=0x360 (MCID 字段只实现到 6，CID7 截断)
```

| 旋钮 | 回读 | 判定 |
|------|------|------|
| region 使能 CFGR.BREN | 0x101 → BREN=1 | ✅ 生效（非 RAZ/WI） |
| region 边界 ST/EN | 0x62000 / 0x62fff | ✅ 精确覆盖缓冲（buf@0x34062de0） |
| region 白名单 CIDCFGR | 0x00030003 | ✅ CID0+CID1 读写，与写入一致 |
| 主设备 CID override RIMC_ATTR[8] | `wrote==readback`（CID0..6） | ✅ 粘住（非 RAZ/WI） |
| **DMA2D 写 SRAM** | **CID 0..7 全部 dropped** | ❌ **含 CID1** |

### 机制定论（无需解释即成立）

四个固件可见旋钮（region 使能、边界、白名单、主设备 CID）**全部回读=写入值**，
DMA2D→SRAM 写仍对所有 CID 被静默丢弃。尤其 **CID1**：region 白名单含它、
RIMC 把 DMA2D 呈现为它、CPU 自己每周期用它写这同一块 SRAM 都正常——但
DMA2D@CID1 被拦。**能区分「CPU@CID1 通过」与「DMA2D@CID1 被拦」的判据，
不可能是 region 白名单**（白名单只按 CID 匹配，二者 CID 相同），只能是
**主设备身份本身**。即：RIMC_ATTR 是个能回读的影子寄存器，其值不被总线级
enforcement 采信；或存在固件够不到的第二道 RIF/compartment 检查。

**净结论**：**DEV boot 下 NuttX 无法靠 region + RIMC 配置解锁 DMA→SRAM——
已用寄存器回读 MEASURED 排除。** 换 RISAF21/22 另建 region 也无济于事：哪个
实例管辖一笔事务由缓冲**物理地址**决定（静态缓冲在 0x34000000 就归 RISAF2，
不能改选），且主设备身份判据与实例无关。ADR-029/032/036 在 DEV boot 保持
PARTIAL。FSBL/secure-world 能否改变主设备总线级身份归属**未测**，不作断言。
安全性：整套回归两次均 PASSED，CPU 全程未被锁死，寄存器按位还原，可逆。

## 理由

flash 启动**技术可行、风险可控（可逆、不烧熔丝、有 DFU 安全网）、且是产品
掉电稳定启动的必选项**——这是本 ADR 唯一非它不可的核心目标。

> **更正历史（2026-07-31，两轮）**：早先把「解锁 RISAF 受限的 DMA/NPU」当成
> 必须 FSBL 的理由；随后据 ST RIF 文档 + `risaf_probe` 一度改判为「NuttX 早期
> 启动即可解锁，不必 FSBL」。**后者已被 `dma2d_unlock` 带回读真机实测证伪**
> （见「决定性更正」节）：region + RIMC 均确认生效，DMA2D 写 SRAM 仍被拦
> （含 CID1），门在主设备总线身份、非 region 白名单。故 DMA→SRAM 解锁**不是**
> 本 ADR（也不是任何 NuttX 早期启动方案）能交付的——DEV boot 下已 MEASURED
> 排除；能否靠 FSBL/secure-world 解属未测。本 ADR 的正当性**仅**建立在掉电
> 持久冷启动这一独立且确凿的产品需求上，与 RISAF/DMA 解锁无关（见
> [[hw-stm32n6-risaf-dma2d-grantable-gpdma-not]]、
> [[hw-stm32n6-risaf-cidcfgr-writable-region-blocks]]）。

- 2026-07-31: Proposed。固化 flash-boot + FSBL/RISAF 路线与分阶段计划，
  记录 RISAF 定义、砖机可逆性、开发调试权衡、最大未知（flash-boot 默认

- 2026-07-31: 新增 `risaf_probe` 并真机 MEASURED。实测 RISAF21 REG[0]
  CIDCFGR 写 `0x00FF00FF` 读回 `0x00030003`（三态里的 PARTIAL）：CIDCFGR
  对 NuttX **可写**（CID0/1 位粘住），修正早先「锁死到更高特权」的推断；
  但只实现 2 个 compartment。
- 2026-07-31: **重大更正（ST 官方 RIF 文档背书）**。经 ST community + RIF
  文档确认：M55 在 DEV boot 是 TDCID（CID 硬连线=1），有权配置 RISAF；
  "fixed after ROM" 冻结的是「谁是可信域」的身份，不是「RISAF 配置被锁」。
  据此推翻早先「RISAF 解锁必须 FSBL」的结论——**解锁 DMA→SRAM 属 DEV-boot
  NuttX 早期 `__start` 可做的独立小专题，不必 FSBL**。两个 app 探针看似
  「被拦」的真因：dma2d 只开了主设备侧 CID（锁①），risaf 只写了禁用的
  scratch region，**都没做「给 DMA 缓冲划专属活跃 region 并授权其 CID」
  （锁②）**。本 ADR 范围收敛为**唯一核心目标 = 掉电持久冷启动（目标 B）**；
  ADR-029/032/036 改由该独立小专题解锁，不再列为被本 ADR 阻塞。同步更正
  上下文/决策/设计/实施/验证/理由/依赖各节与相关 memory。
- 2026-07-31: **决定性更正（`dma2d_unlock` 带寄存器回读真机 MEASURED）**。
  上一条主张的「锁②配方（专属 region + 授权 DMA CID）能在 NuttX 解锁」被
  真机**证伪**。`dma2d_unlock` 精确照配方在 RISAF2 建 region 覆盖 DMA2D
  缓冲、使能、白名单 CID0|CID1，并逐一设 DMA2D 的 RIMC CID——**回读证明
  region（CFGR=0x101 BREN=1、边界、白名单）与 RIMC override 全部生效**，
  但 DMA2D 写 SRAM 对 CID 0..7 仍全部被丢，**含 CID1**（白名单里有、CPU 用它
  写同块 SRAM 正常）。判据：CPU@CID1 通过而 DMA2D@CID1 被拦、二者 CID 相同
  → 拦截依据是**主设备身份**，非 region 白名单、非 RIMC 可写性。结论：
  **DEV boot 下 NuttX 无法解锁 DMA→SRAM（已 MEASURED 排除任何 region+RIMC
  方案）**；ADR-029/032/036 在 DEV boot 保持 PARTIAL，无 NuttX 侧解法；FSBL/
  secure-world 能否解属未测、不作断言。新增「决定性更正」节与 `dma2d_unlock`
  builtin，同步更正状态/范围/理由/依赖/文件各节与相关 memory。上两条 ST 文档
  推理保留为演进记录，结论以本条为准。
